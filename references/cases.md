# 匿名案例：哪些结论可以迁移

| 案例 | 现场对照和处理 | 验证边界 |
|---|---|---|
| 系统选路正常，Codex 首轮重连 | 同一网络关 TUN，原生运行时忽略系统代理时超时，临时启用后握手成功。备份并保存用户级设置，重启后真实会话完成。 | 适用于开关对照有效的机器。另一台健康电脑虽有历史错名记录，却无活动 PPP，系统选路和握手正常，保留原状。 |
| K：活动拨号的正名缺失 | 普通浏览器超时，显式代理成功。LAN 与活动 PPP 在 WinINet 中有正确代理，但当前用户接口返回空。刷新和重新应用原标志无效。核实唯一可逆错名及其原始数据，备份后补入正名。两个网址转为本机代理，再启用 Codex 系统代理并得到 HTTP 101。 | 用户反馈普通浏览器和新聊天恢复。交付记录没有覆盖长期启停同步。 |
| Z：节点故障与拨号选路叠加 | 初始显式请求在 TLS 阶段失败。换可用节点后小请求成功，普通浏览器仍超时。原始检查摘录显示 LAN 手动启用、活动 PPP 手动关闭，两者都保存了本机端点。正名缺失且有唯一可逆候选；补入正名后，系统选路和正文下载恢复。 | TCP 可达和 curl 握手错误不足以定位到哪一段设备。这轮反馈记录为当时未安装 Codex；后续一轮已有桌面端实测。 |
| Z：代理关闭后直连也失败 | 客户端退出，本机监听消失；错名记录已关闭，新增正名仍启用，浏览器访问原本可直连的网站报代理连接失败。回滚本次新增项后直连恢复。再启用客户端时，正名缺失的旧症状复现，重新补入后代理访问恢复。 | 证实补值可以短期恢复代理，也证实该机器的手动补值没有随启停同步。长期稳定方案和 TUN 在该回合未完成验收。 |
| Z 后续复测：一次性修复后，关代理仍会断网 | 退出客户端后，已补的拨号正名仍启用本机端口。此时显式直连国内站点返回 200，原来需手动运行脚本。现场改为当前用户登录启动单个同步进程，读取系统开关与监听状态，只更新活动拨号连接。模拟关代理后，系统返回 DIRECT，国内站点 200；模拟开启后，拨号连接恢复本机端点。 | 现场确认了启动项和一个运行实例。实际托盘切换、完全退出代理客户端及重新登录 Windows 均待验。做法见[持续同步](ppp-sync.md)。 |
| Z 同轮 Codex 复测：HTTPS 通，模型流重试 | 同一节点、TUN 关闭。默认配置下 WebSocket 超时并回退 HTTP；临时启用 `respect_system_proxy` 后返回 101。备份后用原生命令保存。默认参数下网络诊断四项通过，单独启动的模型进程取得完整回复。 | 用户完全退出并重开 Codex 后再次握手成功。复查截至当日 10:05，未见新增同类连续重连或 HTTP 回退；报告未单列重启后从普通图标新建聊天及空闲后追问的结果。使用 Codex 时代理保持开启。 |
| 多台设备：直连节点 -1、同源域名入口可用 | 多位使用者反馈同一服务端的域名入口（CDN、WebSocket、TLS）可用，而 IP 直连入口失败；另有网络可用直连。保留已通入口，分别查直连 TCP 和会话。 | 对照同时改变入口、端口、传输和协议，不足以认定封锁、特定厂商故障，也没有证明客户端注册表需要修改。 |

案例中的名称、地址和配置值不能作为其他机器的写入输入。复盘只保留决定下一步的观察，原始反馈和可识别环境信息不随包分发。
