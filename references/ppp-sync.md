# 关代理后仍被送到本地端口

适用于 Windows 自身负责拨号、使用系统手动代理，并且一次性修复后故障随开关反复出现的机器。先在[系统代理检查](windows.md)确认当前活动的 PPP 连接。节点真连接为 `-1`、更换入口即恢复时，先走[入口诊断](paths.md)。

## 先证实哪一项没有随开关更新

保持拨号连接，关闭 TUN，以平时打开的普通浏览器访问一个本网络原本可直连的公开网页。记录关闭系统代理后浏览器的错误。用户要求强制代理时跳过直连测试，按其原有策略验收。用 PowerShell 对同一网址做一次显式直连 GET，保留状态码、下载字节数和 curl 退出码。该命令仅对本次请求绕过应用代理。[curl 参数说明](https://curl.se/docs/manpage.html#--noproxy)

```powershell
$site = Read-Host '本网络能直连的公开 HTTPS 网页，不含账号或登录参数'
curl.exe -q --noproxy '*' --max-time 20 -sS -o NUL -w "HTTP=%{http_code} bytes=%{size_download}\n" $site
"curl exit=$LASTEXITCODE"
```

在同一用户的普通新进程里，可对同一目标查询系统选路（沿用或重新输入上面的公开网址）。只报告直连、本机端口或其他代理。

```powershell
$target = [uri](Read-Host '输入刚才测试的同一公开 HTTPS 网址')
$route = [System.Net.WebRequest]::GetSystemWebProxy().GetProxy($target)
if (-not $route -or $route -eq $target) { 'DIRECT' }
elseif ($route.IsLoopback) { "本机代理 $($route.Port)" }
else { '其他代理' }
```

若显式直连也失败，先核对拨号是否在线，并从同一网络用另一个已知可直连目标复测。若显式成功、普通浏览器报 `ERR_PROXY_CONNECTION_FAILED`，在开和关时分别运行检查器。对照客户端的实际操作、LAN/默认手动开关、活动拨号正名、当前用户接口、具体网址的选路和监听。只有默认开关确实随操作变化、活动拨号记录仍固定在旧状态，才进入持续同步。发现已有手动修复脚本时，先只读核对它读取什么、写哪个连接、何时触发。

## 让活动拨号连接跟随系统代理

先试客户端支持的每连接设置，按下表现场验收。已有同步进程时先核对当前用户、启动来源和实例数，避免两个进程相互覆盖。若问题可以稳定复现，客户端自身无法维护该连接，且机主同意登录常驻，可采用 Z 验证过的做法：在当前用户会话运行一个同步进程。Z 反馈提供了其行为和测试结果，原程序及源代码未随反馈提供。包里的系统检查器用于只读采样。

| 经现场确认的开关意图 | 监听情况 | 活动拨号连接应做什么 |
|---|---|---|
| 关系统代理，且原基线为直连 | 有或无 | 恢复该连接的直连基线。客户端可继续监听，普通浏览器应能直连原目标。 |
| 开系统代理，指向已经核实的本机端点 | 有，且由预期代理核心提供 | 当拨号设置与预期不同才更新，核对实际网址已选本机代理。 |
| 开系统代理，刚启动、换节点或重载核心 | 刚缺失一次 | 等待核心启动并连续采样；一次探测失败就报告待复核。 |
| 开系统代理，但同一核心的监听持续缺失 | 连续确认缺失 | 若原基线允许直连，且拨号记录仍启用本工具管理的死端口，仅在该连接撤下残留；监听恢复且开关仍开时再启用。若用户要求强制代理，则保留限制并报告监听故障。 |
| 无活动 PPP、活动连接改变、策略受管、PAC 或其他代理接管 | 任意 | 暂停写入，重新确认目标和权属。Wi-Fi 或由路由器拨号时按实际系统选路排查。 |

在现场实现或复核同步器时，以客户端开关实际写入、经过开关对照验证的设置为输入；作为修复目标的拨号记录不能同时充当开关依据。只处理一个已确认的当前用户活动连接和已知本机端口。已有上游、强制代理及其他网络模式按原有策略处理。每次写入前复查连接与当前值，保留其他连接、例外和未涉及的设置；写后从新进程查询实际选路。如果写后读回不符或客户端持续反向覆盖，停止写入。Windows 提供按连接读写 Internet 选项的接口。[微软 WinINet 连接选项](https://learn.microsoft.com/en-us/windows/win32/wininet/setting-and-retrieving-internet-options)

先备份目标项的原始存在性、内容及当前用户启动项，在前台完成一次启停对照，再按授权登记当前用户登录时启动；重复运行应维持一个实例。回滚顺序是先停用本次登记的登录入口、结束已核实的同步实例，再按原始备份仅还原本次管理的连接设置。若改过一个原有登录入口，恢复该入口此前的配置；原先不存在的入口只撤销本次新增项。还原前比对当前值和本次最后写入值，若期间有其他编辑，先保留并逐项合并。恢复后重新查询有效选路，并用普通浏览器复测。

## 按用户平时的动作验收

使用同一张网、同一节点。每个阶段新开检查器进程，将“用户动作、监听、拨号代理、实际选路、普通浏览器结果”记在同一行。

1. **启用。** 平时的图标打开浏览器，加载经代理网站的实际正文。
2. **只在托盘关闭系统代理。** 客户端仍在运行。普通浏览器能打开原本可直连的网站。
3. **从代理开启状态直接正常退出客户端。** 检查端口、有效选路和同一可直连网页，确认用户无需再点手动修复。
4. **重新打开客户端并启用系统代理。** 同一代理网站恢复。若用户也使用 Codex，保持代理开启，继续[重连和工作空间验收](codex.md)。
5. **若部署了登录启动。** 等机主方便时实际重新登录 Windows，确认只有一个相应同步进程、拨号建立后有效选路和真实网页都符合当前开关。仅查到启动项或当前进程时，将“下次登录”列为待验。

模拟 Windows 开关可以验证同步逻辑；交付时逐项写明哪些动作由机主实际完成。在每项已测试的边界内报告结果。
