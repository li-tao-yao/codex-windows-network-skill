# 从入口到网站：定位第一处失败

先确认“延迟”是 ICMP、TCP 还是真连接测试，使用目标配置中实际的地址、端口和协议。下面的交互式示例仅在本机输入地址，无需把服务器信息发给 AI。

```powershell
$entry = Read-Host '当前要测的 TCP 节点入口（域名或 IP）'
$port = [int](Read-Host '该节点 TCP 端口')
Test-NetConnection -ComputerName $entry -Port $port | Select-Object InterfaceAlias,TcpTestSucceeded
```

该命令适用于 TCP 入口。对使用其他传输的节点，用客户端相应诊断。记录网卡和 TUN 状态。测试“原网络直达入口”时，可在现场允许的情况下暂时断开其他 VPN/TUN，结束后恢复。若必须保留隧道，标明测的是经隧道的路径。

**再验证经过节点的实际请求。** 保持客户端运行，设为活动节点，使用界面显示的本机 SOCKS/混合端口；使用 HTTP 入站时将下例协议换成 http。目标选用户实际关心、预期经该节点访问的公开 HTTPS 页面，确认分流日志对应出站。命令做完整 GET，丢弃正文：

```powershell
$localPort = [int](Read-Host '本地 SOCKS 或混合端口')
$site = Read-Host '要测试的公开 HTTPS 网址，不含登录参数'
curl.exe -q -x "socks5h://127.0.0.1:$localPort" --noproxy localhost,127.0.0.1 --max-time 25 -sS -o NUL -w "HTTP=%{http_code} bytes=%{size_download} total=%{time_total}s\n" $site
```

| 观察 | 下一步 |
|---|---|
| 故障入口 TCP 失败，同机对照入口成功 | 保持同一节点和客户端，换一个已知可用的网络，或同一网络换已知正常设备。若结果随出口而变，按时间核对自有服务端入站与回包，再联系相应服务方。 |
| TCP 成功，显式请求仍超时、重置或 TLS 失败 | 从本地监听、节点握手、服务端出站、目标 TLS 顺序定位。与已知可用节点访问相同目标。能拿到服务端证据时再归因于具体哪一段。 |
| 自己的机场可用、自建入口失败 | 若在同一个客户端，固定核心、TUN、分流和目标后只切节点。若使用独立 VPN，分轮运行；切回自建入口前退出独立 VPN，避免误走中转。 |
| 同一 VPS 的域名/CDN 入口能用，而直连入口显示 -1 | 先确认域名实际解析到边缘还是源站。若客户端先连 CDN，观察支持“该入口可用”。IP、端口、协议、握手和回源可能同时变化，需用上面的 TCP/握手证据再定位。 |
| 显式访问成功，普通浏览器超时 | 转[Windows 系统代理分支](windows.md)。只有测速失败而实际访问正常时，核对测试网址和超时时限。 |

HTTP 000 表示没有拿到 HTTP 状态；保留 curl 自身错误码。403/429 表示目标或其边缘已响应，需按真实应用结果分析。Schannel 35 的错误本身不足以确定是节点服务器或吊销服务的问题。保留正常证书和吊销校验，结合系统时间、证书链、相关服务可达性和系统日志定位。不同目标、代理路径或校验参数的结果分开记录。
